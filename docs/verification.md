# Verification

## Approach

1. **The CPU is reused, not re-verified.** Hazard3 is silicon-proven (RP2350) and was verified with riscv-formal by its author. We test the integration: fetch from SRAM, byte/halfword/word accesses through our fabric, register accesses, blocking wait states.
2. **Protocols are tested end to end with real firmware.** Every test builds a C program with stock GCC, loads it over the host SPI port exactly as the board MCU would, runs it on the RTL, and watches the pins.
3. **Protocol correctness is judged by independent peer models.** Each model is written from the protocol's specification or a device datasheet, not from our RTL: it decodes what the chip sends, checks timing rules, and answers as a real device or host would. A test passes only if the model is satisfied *and* the firmware reports success.
4. **Evidence levels.** Each claim says whether it comes from RTL simulation, gate-level simulation, P&R sign-off, or (later) FPGA.

## Test list (RTL simulation, `test/`, `make -C test`)

`make -C test` runs the default list with Icarus (also the CI simulator). `make -C test SIM=verilator EXTENDED=yes` adds the tests that need tens of milliseconds of bus time at the protocols' real speeds; Verilator runs them about 30 times faster (the whole set in about 11 minutes). Icarus stays the reference because it models X. Every protocol and its model are also listed in [protocols.md](protocols.md).

## Do the models fail when they should?

Each new model was run against a deliberately broken copy of its firmware and had to reject it (`make SIM=verilator`, 2026-11-19): a 12-bit LIN BREAK; a SENT CRC with the wrong seed; HDLC without zero insertion; an MDIO write turnaround of 11; an SD CRC7 with the wrong polynomial; a Modbus CRC with the wrong polynomial; a 50 us 1-Wire presence pulse; even parity from the PS/2 device; DALI sent LSB first. All nine fail their tests. Older models were checked the same way earlier (see `ai_use.md`).

## What the models found

Independent models catch mistakes in both the RTL and the test itself. Examples from development:

- RTL: after a UART frame with a low stop bit, the receiver started a phantom frame because it reacted to the line *level*. Fixed: start on an *edge* from idle, and drop a frame whose start bit is gone at mid-bit (glitch filter).
- RTL design gaps found while writing the I2C and USB tests: an external-clock engine must change data only on the launch edge (otherwise an I2C target would make a false START/STOP); a pre-queued auto-reply must not fire on a packet that ended before it was queued; cancelling a queued answer must not reset the receiver.
- Board-level issue found by the CAN model: after reset all `uo` outputs are 0, which on a CAN TXD is *dominant* and would block the bus while the program loads. CAN TXD therefore goes on a `uio` pin, which is high-impedance until the program enables the engine.
- RTL, found by `test_queue`: the host port only used SRAM cycles the CPU left idle. With four jobs running, the CPU used the port nearly every cycle, the host waited longer than one SPI byte, and the next byte overwrote the pending one, so a freshly loaded job had three missing bytes and trapped. Fixed in `pg_ahb.v` (the host now has priority, one CPU wait cycle per host byte); `test_boot` has a regression test that keeps the port 100 % busy.
- Firmware structure, found by `test_mixed`: with four tasks sharing one CPU, every task step must be shorter than the tightest FIFO allows (four UART bytes at 1 Mbaud = 2000 cycles). The CAN frame parser took longer, bit by bit, and the UART lost a byte; it now works on whole words with shifts.
- RTL, found by the SD card model: with a delayed MISO sample point (`RX_DELAY`, needed above F/8) the sample of a word's last bit came after the next, shorter word had started, so it was counted with the wrong length and the words slipped; a command of 8 + 32 + 7 + 1 bits then never completed. The length is now latched at the nominal sample point.
- RTL, found by the USB tests after adding the SYNC hunt: the glitch filter treated "no bit counted yet" as "first sample of the frame". With the hunt, the first bit after SYNC is also uncounted, so an ACK (whose PID starts with a 0, the idle level after NRZI) was dropped as a glitch; SETUP, DATA and IN PIDs start with a 1, which hid it. The filter now uses its own first-sample flag.
- RTL, found by the DALI test: the Manchester frame-end window is 2 bit periods, which at 1200 bit/s (41,667 cycles per bit) overflowed the 16-bit timer; it is 17 bits now.
- Firmware, found by the LIN model: the first BREAK went out before the bus had been recessive for a bit after configuration, and a BREAK started in the middle of the slave's last stop bit.
- Firmware timing at USB full speed (12 Mbit/s, a byte every 32 cycles): reading the RX FIFO byte by byte inside the main event loop was too slow, so the engine now drops the SYNC and delivers 16-bit words and C reads a packet in a tight loop; computing a token CRC5 (about 250 cycles) inside the 400-cycle window between a SETUP and its DATA was too slow, so the expected token is computed once per address; the status-stage ACK is queued when the last IN data is acknowledged, because the OUT token and its empty DATA packet arrive within about 150 cycles. Found by the host model's turnaround and response checks.
- Firmware, found by the device model in `test_usb_host`: the receive timeout started while the host's own packet was still being sent, and a packet pushed while the previous one was finishing followed it without the EOP's J state.
- Measured limits, written down instead of hidden: 10BASE-T receive tolerates +/-5 ns of independent jitter per edge at 50 MHz and +/-8 ns at 60 MHz (IEEE 802.3 allows +/-13.5 ns at a receiver, most of it slow cable ISI); a first run at +/-13.5 ns failed, which is how the bound was found. One CPU serves both directions in `eth_ping`, so a frame that arrives while a reply is being sent overflows the RX FIFO.
- Test-side bugs (the RTL was right): a DALI model that updated the wired-AND bus only while it was not busy itself, a PS/2 host model that sent the next byte before the keyboard had answered the previous one, a CEC model that required EOM on a frame the initiator rightly abandoned after a missing ACK, an I2C controller model that released SDA for START, an EEPROM model that took a repeated START's SCL rise for a data bit, a 1-Wire model that took its own presence release for a reset.

## Gate level and sign-off

- P&R sign-off of the full design (four engines): LVS clean, KLayout DRC clean, antenna clean, setup/hold met at 50 MHz in all corners (+2.91 ns setup slack at the slow corner, +0.04 ns hold slack at the fast corner), Tiny Tapeout precheck passes *(P&R, local LibreLane run and local precheck, 2026-11-19; the official Tiny Tapeout GDS workflow on GitHub also passed GDS, precheck and gate-level tests on the earlier revisions, 2026-11-13 and 2026-11-14)*.
- Gate-level simulation of the routed netlist (`make -C test GATES=yes`, Icarus 13 with the IHP cell and SRAM models): SPI load and read-back, `memtest`, `blink`, host access while the CPU keeps the SRAM busy, all three UART tests, the four-engine `test_quad`, the three CAN tests (including the receiver ACK), the SWD host and 10BASE-T receive at 50 and 60 MHz (Manchester clock recovery on engine 1) pass *(gate-level simulation of the current layout, local, 2026-11-19; earlier layouts also in the Tiny Tapeout GDS workflow, 2026-11-14)*. `test_tgpio` reads the RTL's cycle counter by name and is skipped at gate level.
- What gate level found: registers that a program never writes are X in simulation; a speculative register read let that X spread through the pipeline and stopped the CPU (silicon would just hold a random, unused value). The startup code now clears every register (22 bytes), and the CPU clears x0's register-file entry in reset.

## FPGA

The same RTL builds for an AMD Zynq UltraScale+ board (ALIENTEK DFZU2EG, `fpga/`): the SRAM macro becomes a block RAM with the same read timing, the chip's 24 pins go to a 3.3 V header, and an FPGA-only UART bridge lets a PC be the host. The whole chip takes 11 % of the FPGA's LUTs and meets 50 MHz with 12 ns of setup slack *(FPGA place and route, Vivado 2025.2)*. The bridge is simulated with the chip RTL: a program is loaded, read back and run, and a counter is read while the CPU runs *(RTL simulation)*. Running it on the board, against real devices, is still to do.
